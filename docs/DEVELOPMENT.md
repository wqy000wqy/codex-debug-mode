# 开发与维护

## 修改与构建

需要 Node.js 22+ 和 npm。不要直接编辑 `plugins/debug-mode/` 的生成文件。

```sh
npm ci
npm run build
npm run check:package
```

根 `package.json` 管理版本和依赖锁。修改工作流时编辑 `src/workflow.mjs`；构建会同步生成技能说明与插件载荷。提交源码、锁文件、生成包和市场目录，使安装者无需自行构建。

构建通过 esbuild 将 SDK 和运行依赖打包进服务，保留 Node 内置模块引用，并附依赖许可和 SHA-256 清单。`check:package` 检查文件清单、版本、清单配置、工作流同步和哈希；它不是运行时验收，也不代表所有宿主版本兼容。

仓库保留了工作流与 MCP 回归脚本，按需运行：

```sh
npm run test:workflow
npm run test:mcp
```

发布前建议在独立 Codex 会话实际验收安装、右侧展开、日志接收、继续分析、标记为已修复和关闭标签页。记录执行过的验证及未覆盖范围。

## 发布更新

1. 修改 `src/`，更新根 `package.json` 的版本以及 CHANGELOG。
2. 同步 package-lock，执行构建与静态检查。
3. 检查 Git 差异，确保没有个人路径、调试日志、会话数据或凭证。
4. 提交并推送源码及 `plugins/debug-mode/`。同事刷新市场后更新。

插件 ID、MCP 服务名和数据目录标识固定为 `debug-mode`。重命名这些标识会影响升级与会话识别，应单独设计迁移。

## 排障

### 没有可调用工具

确认插件已安装、连接并启用。旧会话可能仍使用旧的工具目录，先新开会话再选择插件。技能可见不等于 MCP 服务已经连接成功。

### 无法启动本机服务

启动器依次查找用户指定的 `CODEX_DEBUG_NODE_PATH`、宿主提供的 `CODEX_MCP_NODE_PATH`、PATH 中的 node，以及常见 macOS 安装路径。需要可执行的 Node.js 22+。

用户指定 CODEX_DEBUG_NODE_PATH 后，该选择具有优先权；无效时会报错，不会偷偷切换。若桌面应用未继承终端环境，请通过宿主支持的 MCP 环境配置指定运行时，或让兼容 node 出现在桌面应用可见的 PATH 中。启动器不下载工具链。

### 已复现但日志为 0

先看浏览器网络面板中的埋点请求：连接被拒绝通常表示接收服务未监听对应地址或端口。核对当前面板会话的接收地址、服务状态，以及页面运行的是否确实是最新带埋点版本。浏览器 CSP、跨域限制和运行环境不同也可能阻止发送。

不要把“点击继续分析”当作开启采集的开关；复现期间接收服务就应工作。不同电脑的 localhost 指向各自电脑，远程页面不能直接向开发者电脑的回环地址发送。

### 面板没有自动打开

依赖宿主 MCP Apps 的 fullscreen 展示支持。在 Codex 中该模式对应右侧应用标签页，不等同于系统全屏。工作流准备完成后才应调用展示工具；面板自身不控制宿主自动生成的代码变更摘要。

## 数据与兼容性

旧原型和团队版使用不同插件与数据标识，本版本不搬运或删除旧原型数据。Git 中只包含源码和分发载荷，不包含用户会话。当前未声明 Windows 支持；Linux 启动和桌面宿主行为尚待验收。
